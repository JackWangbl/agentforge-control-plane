1. 文档说明与目标

AgentForge Control Plane 是本机可运行的 企业 Agent 管理控制面，不是又一个聊天机器人。 FastAPI 同时提供 REST 与静态管理台；业务数据默认落 MySQL（开发测试可用 SQLite）。 管理台地址：http://127.0.0.1:8080，OpenAPI 在 /docs。

1.1 要解决的问题

  • 谁能看、谁能改：租户 + 角色权限；默认属主可见，同租户可按角色共享，跨租户不可见。
  • Agent 用什么干活：模型、Skill 规程、MCP / 浏览器工具、沙箱策略的集中登记与绑定。
  • 对话能不能复盘：会话、消息、本地 Trace，可选推送到 AgentScope Studio / Langfuse。
  • 质量靠什么证明：数据集回归、在线抽检 / 离线评测、A/B 分流实验。

1.2 非目标（当前版本不做）

  • 对外多租户 SaaS 的物理隔离（独立库、独立 VPC、独立 K8s Namespace）。
  • 把 Agent 推理进程做成每租户独立运行时或服务网格。
  • 完整 RAG 知识库产品（本仓库内置的 search_knowledge 只检索已登记 Skill 正文）。
  • 工作流编排的生产级执行引擎（Workflow.graph 可保存 DAG，执行校验与调度尚未作为主路径）。

1.3 设计原则

  1. 控制面与模型解耦：聊天走 OpenAI 兼容 /chat/completions，未安装 AgentScope 也能跑通控制面。
  2. 绑定才生效：Skill / MCP / 沙箱必须挂到 Agent；未绑定的工具名在运行时拒绝。
  3. 失败可续跑：调试台把进行中状态写入 workspace checkpoint，支持 /playground/resume。
  4. 没有密钥不假装已调用：缺凭证时走预览回复，并在链路里标明 preview。
  5. 租户 ID 不信任模型：工具侧使用服务端 ExecutionContext，模型参数里的 tenant_id 不作授权依据。
  6. 沙箱默认不回退宿主机：Docker 不可用时拒绝在控制面主机执行用户代码。

2.4 请求与数据流

正常 Agent 入口是调试台，而不是独立的推理集群。

管理台→ 鉴权 RBAC→ POST /api/playground/run→ 拼提示+工具→ 模型 HTTP→ 工具/沙箱→ 落会话/Trace→ Studio 导出

评测任务复用同一套 generate_chat_reply，因此 Skill、MCP、沙箱在回归里同样生效。 离线评测写入 evaluation_runs.status=queued，由启动时拉起的 daemon 线程领取。

5. 身份、租户与权限

5.1 认证

  • 登录：POST /api/auth/login，PBKDF2-HMAC-SHA256（约 12 万轮），签发随机 Bearer，TTL 7 天，落 auth_tokens。
  • 请求：Authorization: Bearer；平台管理员可用 X-Tenant-Id 切换工作租户，普通用户禁止。
  • 权限：角色 JSON 权限点；* 与 platform:admin 视为全权限。

5.2 授权模型

对齐 AgentScope「默认属主可见」：

  1. 查询先按 tenant_id == 当前租户 OR tenant_id IS NULL 过滤。
  2. 属主（owner_id 为空或等于自己）可见可写（还需具备 write 权限点）。
  3. TenantSharePolicy：同租户且具备对应 read/write 的成员，可看见（及编辑）他人资源。
  4. 跨租户：get_row 返回 404，不暴露存在性。
权限点分组
* / platform:admin / tenant:admin平台与租户
user:* / role:*IAM
agent / mcp / skill / model / workflow / sandbox 的 read、write构建
session:read|write、trace:read运行
eval:read|run、experiment:read|write质量

种子角色大致为：平台管理员（全权限）、开发者（构建+评测）、审计员（会话与链路只读）、演示账号。

5.3 跨资源引用

Agent 绑定 Skill / MCP / Sandbox 时，validate_agent_bindings 要求 ID 必须属于同一 tenant_id，否则 422。 运行时 selected_skills / selected_mcps / selected_sandbox 再滤一遍，历史脏绑定会被忽略。

6. Agent 运行时（调试台入口）

主入口：POST /api/playground/run 与 POST /api/playground/resume。需要 session:write 与 agent:write。

6.1 准入

  1. 解析 Agent、模型配置；模型 disabled 则 409。
  2. 若带 experiment_id 且实验为 running，按策略分流，可能改写实际 Agent；holdout 仍用所选 Agent。
  3. 会话不得跨租户、不得跨 Agent 工作空间（实验场景会新开会话）。
  4. 历史优先读 workspace 会话文件，否则回落 chat_messages。

6.2 generate_chat_reply

  1. 创建 ExecutionContext(tenant_id, agent_id, execution_id) 写入 ContextVar。
  2. 无密钥：预览回复；时间类问题若绑定了 get_current_time 仍可调工具。mode=preview。
  3. 有密钥：拼系统提示（人设 + 已绑 Skill 正文 + 工具提示）；组装 OpenAI tools（MCP + 可选沙箱 spec）。
  4. 循环调用 complete_chat（最多 4 轮；含 browser_ 工具时 8 轮）。模型返回 tool_calls 则在控制面执行，结果以 role=tool 回灌。
  5. 未授权工具名直接返回错误 JSON，不执行。
  6. 异常写入 checkpoint（status=failed），回复中带错误摘要（密钥已脱敏）。
  7. finally：关闭本轮 browser scope，复位 ExecutionContext。

6.3 返回前落盘

_finalize_playground 同步完成：

  • 写 ChatMessage、更新或创建 Conversation、写 Trace.spans。
  • persist_run 写入 Agent workspace 的 sessions / traces JSON。
  • 同步 HTTP 导出 AgentScope Studio（短超时，失败不影响主流程语义但仍占用返回路径）。
  • 若走实验，记 ExperimentEvent。
运行时形态
Agent「在跑」等于控制面进程内的一次同步函数。推理是出站 HTTP，不是独立 Agent 进程。 高并发时会占满 uvicorn 线程（complete_chat 超时 45s）。评测工人目前也是同进程单线程轮询。

7. 能力注册：Skill / MCP / 浏览器 / 沙箱

7.1 Skill

Skill 是给模型看的 Markdown 规程，不是可执行包。来源可以是库内 instruction 或仓库 skills/*/SKILL.md。 绑定后由 skill_prompt_block 拼进系统提示。

7.2 MCP

传输行为
HTTP Stream（推荐）Streamable HTTP 探测、列出 tools、运行时 call_tool
SSE / StdIO登记与展示；远程调用以 HTTP Stream 为主路径
内置本地工具get_current_time、calculate、search_knowledge、list_agents
内置浏览器browser_open / text / links / close

远程工具若 schema 含 tenant_id 字段，由服务端覆盖为当前 Agent 租户，不采用模型传入值。

7.3 浏览器

  • 进程内一个 Playwright Chromium；每个 ExecutionContext.scope_key 一个 BrowserContext + Page。
  • 全局锁串行化操作，避免并发打到同一驱动。
  • 默认拒绝 localhost 与非全球单播地址；BROWSER_ALLOW_PRIVATE_NETWORK=1 才放开。
  • 仅 http/https，禁止 URL 内嵌用户名密码。

7.4 沙箱

Agent 未绑沙箱或策略停用时，sandbox_run_python/shell 被拒绝。

后端选用条件隔离
dockerruntime 解析为 docker 镜像且在白名单一次性容器：--rm、read-only 根盘、cap-drop ALL、no-new-privileges、pids/memory/cpu/ulimit、默认 --network none；工作目录 bind-mount。Docker 不可用则报错，不回退宿主机。
agentscope_runtimeruntime 名称像官方镜像且包可用走官方运行时；失败再考虑本地
local仅当 ALLOW_UNSAFE_LOCAL_SANDBOX=1python -I 或 /bin/sh，可选 socket 阻断与内存 preexec。生产默认关闭。

联网沙箱必须配置 SANDBOX_EGRESS_NETWORK。镜像禁止 --pull 自动拉取。

8. 工作空间与检查点

根目录：环境变量 WORKSPACES_DIR，默认仓库下 workspaces/。

workspaces/tenants/{tenant_id}/agents/{agent_id}-{slug}/
    sessions/{session_id}.json
    traces/{trace_id}.json
    files/
    manifest.json

沙箱工作目录：workspaces/_sandboxes/tenant-{id}/policy-{policyId}-{name}/{execution_id}/。 checkpoint 记录 run_id、status、next（llm|tool）、working 消息、pending_tools、已完成 tool id、usage、error。 resume 仅允许 status 为 failed 或 running 的检查点。

9. 质量：数据集、评测、A/B 实验

9.1 数据集

支持手工用例与导入 CSV / JSON / JSONL（最大约 5MB、2000 条）。字段别名覆盖中英文（问题 / input、期望 / expected 等）。 导入 on_duplicate 默认 skip。文件副本落 workspaces/_datasets/{id}/。

9.2 评测

项说明
在线同步，最多 10 条
离线queued → 后台线程每约 1.2s 领取一条 running
打分contains / exact / regex / llm（另选裁判模型）
执行每条用例调用 generate_chat_reply，与调试台同绑定
操作resume（跳过已完成 case）、重跑、取消、导出 CSV

领取任务目前无数据库行锁，多进程部署会存在重复领取风险。见第 15 章。

9.3 A/B 实验

策略粘滞单位
user_hash同一用户哈希到同一变体
session_hash同一会话同一变体
user_first用户首次按权重随机，之后粘滞
random每次请求独立抽，不粘滞

2–6 个变体，权重分流；traffic_percent 可留 holdout。调试台可挂实验。对比接口汇总延迟、Token、状态。

10. 观测

  • 本地 Trace：每次 playground / 评测写 spans（接收消息、解析 Agent、注入 Skill、关联工具、模型调用、工具结果、回复）。
  • AgentScope Studio：登记 run 并推 OTLP；环境变量 AGENTSCOPE_STUDIO_URL。
  • Langfuse：配置公钥/密钥/Host 后导出；缺失则仅本地。
  • 健康检查：GET /api/health、/api/observability。

生产建议：Trace 明细进 OTLP 后端，数据库只留索引与业务标签（见 ARCHITECTURE.md）。

11. 前端管理台

单页应用：侧栏按权限隐藏入口。调试台为会话气泡 + 右侧执行链路；输入栏固定在对话区底部，消息列表单独滚动。 静态资源以 query 版本号刷新缓存。登录态存 localStorage 令牌。

12. 隔离与安全边界

结论先说清楚
租户隔离是应用层逻辑隔离（共享库、共享盘、共享控制面进程）。 Agent 运行主体也在同一进程。物理隔离只出现在「Docker 沙箱成功执行用户代码」这一段。
对象现状不是什么
数据tenant_id 行级过滤 + 属主/同租户分享独立数据库、独立 schema、数据库 RLS 强制
磁盘路径含 tenants/{id}独立卷、独立 OS 用户、强制 chroot
Agent 推理控制面内同步 HTTP每 Agent / 每租户独立进程或 VM
浏览器Playwright Context + 全局锁独立浏览器集群
代码执行短命加固容器（若 Docker 可用）每租户独立 Docker daemon / K8s Namespace

纵深防御已做：绑定双校验、ExecutionContext、沙箱不回退宿主机、浏览器禁私网、密钥接口脱敏。部署层的分库、IAM、NetworkPolicy 仍需另行建设。

逻辑隔离缺口：tenant_id IS NULL 对所有租户可见；部分 name 全局唯一；平台管理员可切换租户。

15. 演进建议

以下尚未实现，作为保护 Agent 入口、支撑更高并发时的设计方向。

15.1 热路径与冷路径

用户等待的是这一轮 reply，不要把整次 generate_chat_reply 丢进任务队列。 会话、checkpoint、返回 JSON 必须同步成功；Studio / Langfuse / 仪表盘汇总可入队。

15.2 限流、舱壁、熔断

按租户 QPS、用户 QPS、Agent 在途、模型供应商在途分层限流。 playground / eval / sandbox / browser 分舱壁。 LLM、单个 MCP、沙箱、Studio 分别熔断；LLM 打开时走现有 checkpoint，不伪装预览成功。

15.3 队列与缓存

Redis：共享令牌桶、熔断状态、配置快照、observe/eval 队列。 评测改为真队列 + 状态机，避免多进程抢同一条 queued。 缓存 Agent/Skill/MCP 快照，不缓存模型生成；密钥不进 Redis 明文。

15.4 物理隔离（合规需要时）

控制面过滤保留作纵深防御。物理边界在部署：每租户 schema 或实例、独立 workspace 卷、 沙箱 Namespace / NetworkPolicy、密钥独立托管。那是拓扑变更，不是再加一个 tenant_id 字段。

15.5 建议落地顺序

  1. P0：complete_chat 异步化；Studio 导出移出返回路径；本进程限流与 LLM 熔断。
  2. P1：Redis 共享配额与评测队列；配置 L2 缓存。
  3. P2：调试台 SSE；配额与熔断可观测；按租户配置限额。
第一刀（若只改一处）
拆 _finalize_playground：会话与 Trace 仍同步 commit；Studio / Langfuse 改为返回后发送。 同时给 complete_chat 增加按 provider 的在途上限。改动面小，对入口 P99 收益最大。
